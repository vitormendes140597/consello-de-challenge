## ADDED Requirements

### Requirement: Load Raw Alert Dataset
The ETL SHALL read a JSON array of raw alert records from a configurable input path, defaulting to `etl/data/raw/sample_alerts.json`.

#### Scenario: Raw alerts are loaded
- **WHEN** the ETL runs with the default input path
- **THEN** it loads every alert object from `etl/data/raw/sample_alerts.json`

#### Scenario: Raw alert source fields are required
- **WHEN** an input alert is missing `id`, `received_at`, `subject`, or `body`
- **THEN** the ETL fails validation before invoking the AI extraction step

### Requirement: Preserve Source Alert Fields
The ETL SHALL preserve each input alert's `id`, `received_at`, `subject`, and `body` unchanged in the corresponding enriched output object.

#### Scenario: Source fields are copied unchanged
- **WHEN** the ETL enriches an alert
- **THEN** the enriched output contains the same `id`, `received_at`, `subject`, and `body` values as the source alert

### Requirement: Extract Structured Alert Metadata
The ETL SHALL use LangChain with an OpenAI backend to extract structured metadata for each alert into the fields `companies`, `sectors`, `geo_markets`, `key_markets`, `commodities`, `regulators`, `macro_sensitivities`, and `themes`.

#### Scenario: Enriched output contains all metadata arrays
- **WHEN** the ETL produces an enriched alert
- **THEN** the output contains `companies`, `sectors`, `geo_markets`, `key_markets`, `commodities`, `regulators`, `macro_sensitivities`, and `themes` arrays

#### Scenario: Empty metadata is represented as an empty array
- **WHEN** no relevant values are extracted for a metadata field
- **THEN** the ETL writes an empty array for that field

### Requirement: Define Output Field Semantics
The ETL SHALL document and implement the semantic meaning of every output field.

The fields `id`, `received_at`, `subject`, and `body` SHALL represent source alert values copied unchanged from the input dataset.

The field `companies` SHALL represent named business entities relevant to the alert, including focal companies, competitors, suppliers, customers, partners, acquirers, acquisition targets, and other operating businesses.

The field `sectors` SHALL represent broad industries or business verticals affected by the alert.

The field `geo_markets` SHALL represent countries or regions materially connected to operations, demand, supply chains, regulation, investment, or manufacturing in the alert.

The field `key_markets` SHALL represent product markets, end markets, customer markets, or demand pools affected by the alert.

The field `commodities` SHALL represent raw materials, traded goods, physical inputs, or components whose availability, pricing, or supply affects the alert.

The field `regulators` SHALL represent regulatory bodies, laws, agencies, enforcement regimes, or formal review processes mentioned or clearly implicated by the alert.

The field `macro_sensitivities` SHALL represent broad economic or geopolitical drivers that can affect valuation, demand, margins, financing, or supply chains.

The field `themes` SHALL represent strategic or investment themes that summarize why the alert matters across companies or markets.

#### Scenario: Output fields have explicit definitions
- **WHEN** a developer reviews the ETL output contract
- **THEN** every output field has a documented meaning and extraction boundary

#### Scenario: Source fields are not generated by AI
- **WHEN** the ETL creates an enriched alert
- **THEN** `id`, `received_at`, `subject`, and `body` are copied from the source alert rather than generated by the AI model

### Requirement: Use Pydantic Structured Output Models
The ETL SHALL define Pydantic models for enriched alert output and SHALL validate each AI extraction result against those models before writing processed JSON.

#### Scenario: Valid structured output is accepted
- **WHEN** the AI extraction result conforms to the Pydantic output model
- **THEN** the ETL includes the validated result in the processed output

#### Scenario: Invalid structured output is rejected
- **WHEN** the AI extraction result does not conform to the Pydantic output model
- **THEN** the ETL reports a validation error and does not silently write malformed processed output

### Requirement: Extract Companies As Business Entities Only
The ETL SHALL include only named business entities in the `companies` array and SHALL NOT include countries, regulators, markets, sectors, commodities, macro sensitivities, or themes in `companies`.

Each company item SHALL contain `name`, `ticker`, and `rationale`. `name` SHALL be lower case. `ticker` SHALL be lower case when present and null when unavailable.

#### Scenario: Company mention is extracted
- **WHEN** an alert mentions a named business entity such as a focal company, competitor, supplier, customer, partner, acquirer, or acquisition target
- **THEN** the ETL includes that entity in `companies` with a lower case name and rationale

#### Scenario: Non-company concept is excluded from companies
- **WHEN** an alert mentions a country, regulator, market, sector, commodity, macro sensitivity, or theme
- **THEN** the ETL does not include that concept in `companies`

#### Scenario: Missing ticker remains null
- **WHEN** a company is extracted but the alert does not provide a ticker and the model has no high-confidence ticker evidence
- **THEN** the company item's `ticker` value is null

### Requirement: Extract Category Metadata With Rationales
The ETL SHALL represent `sectors`, `geo_markets`, `key_markets`, `commodities`, `regulators`, `macro_sensitivities`, and `themes` as arrays of metadata items containing `name` and `rationale`.

Each metadata item `name` SHALL be lower case. Each `rationale` SHALL briefly explain the alert evidence supporting inclusion.

#### Scenario: Category item is extracted with evidence
- **WHEN** an alert contains evidence for a sector, geographic market, key market, commodity, regulator, macro sensitivity, or theme
- **THEN** the corresponding metadata array contains a lower case `name` and concise `rationale`

### Requirement: Apply Field-Specific Extraction Guidance
The ETL SHALL guide the AI model with field-specific inclusion and exclusion instructions rather than closed allowlists for extracted values.

The ETL SHALL define one reusable prompt section for each AI-extracted field: `companies`, `sectors`, `geo_markets`, `key_markets`, `commodities`, `regulators`, `macro_sensitivities`, and `themes`.

Each field prompt section SHALL describe the field purpose, inclusion criteria, exclusion criteria, evidence standard, name normalization expectations, rationale expectations, and field-specific edge cases.

#### Scenario: Client profile is used as context
- **WHEN** the ETL invokes the AI extraction step
- **THEN** it provides available client profile values as contextual hints for the model

#### Scenario: Values outside the client profile can be extracted
- **WHEN** an alert contains a relevant company, market, commodity, regulator, macro sensitivity, or theme not listed in the client profile
- **THEN** the ETL can include that value if the alert text provides sufficient evidence

#### Scenario: Every extracted field has prompt guidance
- **WHEN** the ETL constructs model instructions
- **THEN** it includes prompt guidance for `companies`, `sectors`, `geo_markets`, `key_markets`, `commodities`, `regulators`, `macro_sensitivities`, and `themes`

#### Scenario: Prompt guidance defines boundaries
- **WHEN** a field prompt section is reviewed
- **THEN** it describes what to include, what to exclude, and what evidence is required for that field

### Requirement: Build Synthesis Prompt
The ETL SHALL build a synthesis prompt that combines the alert content, client profile context, global extraction rules, and all field-specific prompt sections into the final model-facing instruction.

The synthesis prompt SHALL be the prompt used by the LangChain/OpenAI structured output invocation.

#### Scenario: Synthesis prompt includes field prompts
- **WHEN** the ETL builds the synthesis prompt for an alert
- **THEN** the prompt includes the prompt section for every AI-extracted field

#### Scenario: Synthesis prompt includes alert content
- **WHEN** the ETL builds the synthesis prompt for an alert
- **THEN** the prompt includes the alert `subject` and `body`

#### Scenario: Synthesis prompt includes global rules
- **WHEN** the ETL builds the synthesis prompt for an alert
- **THEN** the prompt instructs the model to avoid hallucinated facts, use lower case names, return empty arrays when evidence is absent, and provide concise rationales

### Requirement: Normalize And Deduplicate Per Alert
The ETL SHALL normalize extracted names to lower case and SHALL deduplicate items within each metadata array for a single enriched alert.

#### Scenario: Duplicate names in one field are merged
- **WHEN** the AI extraction result contains duplicate names within the same metadata array for an alert
- **THEN** the ETL writes only one item for that name in that array

#### Scenario: Same name can appear across different alerts
- **WHEN** the same company or metadata name is relevant to multiple source alerts
- **THEN** the ETL can include that name independently in each enriched alert

### Requirement: Write Processed Enriched Alert Dataset
The ETL SHALL write the enriched alert dataset as a JSON array to a configurable output path, defaulting to `etl/data/processed/enriched_alerts.json`.

#### Scenario: Processed output is written
- **WHEN** all input alerts are successfully enriched and validated
- **THEN** the ETL writes a JSON array of enriched alert objects to the configured processed output path

#### Scenario: Output count matches input count
- **WHEN** the ETL completes successfully
- **THEN** the processed output contains one enriched object for each input alert
